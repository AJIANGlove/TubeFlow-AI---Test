# Codex 授权与任务续接

确认日期：2026-09-08。适用范围：本 Test 仓库内的 Codex 工作方式；本文件不新增产品 API、恢复能力或工具权限。

## 1. 授权从哪里查

1. 先读全局与本项目 AGENTS，以及 `USER_DECISIONS.md`、`FINAL_ACCEPTANCE_CRITERIA.md`；当前用户明确指令限定本次工作范围。
2. 查 `runtime/operations/AUTHORIZATIONS.md`，按业务项目、任务目标或已知操作 ID 定位相关记录，随后核对用户原话/明确操作及其来源。索引缺项先在既有操作记录和可访问会话中定点查找，不先要求用户重复批准。
3. 授权事实来自用户，业务运行事实来自现有 API、PostgreSQL、Provider 回执和运行审计；助手生成的计划、摘要、勾选框、配置或成功历史均不能自行授予新权限。不要把索引状态当作远端状态。
4. 新会话须匹配仓库、业务项目及原任务目标；会话 ID 是证据位置，不是授权失效条件。同一未完成任务仅在原授权适用范围、有效期和额度内续接，本文件不延长许可；读取记录或仅打开项目不会启动任何生成。
5. `runtime/` 已被 Git 忽略。新工作树、其他机器或缺少本地记录时，先从可核实的原会话/证据恢复记录；仍缺必要信息才集中补问，不假定授权存在或费用为零。不可将任务授权自动迁移为另一业务项目或仓库的许可。

## 2. 如何判断能否继续

- 对象、允许动作、输入约束、外发范围与限制仍在原授权内，且任务未完成、未撤销、拟执行动作的适用额度未耗尽时，继续已授权步骤。已批准修复边界内的提示词修正等派生输入不逐次询问；冻结快照等具体不变要求继续执行。
- 范围实质变化时保留未变化部分，仅询问新增对象、接收方、用途、数据类型、额度或冲突；记录无法对应时先查已有事实，不反复让用户重述整个任务。
- 已完成、撤销或耗尽的许可不能启动新增提交。任务尚在查询/归档阶段时，可在原授权范围继续查原任务；没有新增提交额度不等于应放弃既有任务的恢复查询；零生成额度也不限制已授权的本地文件调整或只读核查。
- 最终效果冲突才适用全局“确认强制执行”门槛；相同具体冲突已有准确批准且仍有效时承接原授权。需要该口令时第一次询问就同时说明冲突、影响、替代方案、对象与限制。普通流程问题不自动套用口令；新冲突不借用旧批准。
- 只读、仅回答、停止等当前明确限制必须遵守，即使记录中有尚未用完的操作许可。

## 3. 外发许可与任务额度

- 本次不启用任何长期外发或付费许可，不增加接收方、数据类型、次数、预算或有效期。未来若需长期外发许可，须先将实际接收方、用途、数据类型、适用项目及有效期列成具体清单，由用户另行明确批准后记录来源；用户可一次批准完整清单，不要求逐行回复。即使有该许可，实际生成仍须匹配具体任务的原授权与额度。
- 以下为配置/代码核对所得候选，长期授权状态均为“待逐项明确批准”；不撤销仍有效且可核实的具体任务授权。本次规则调整批准不将任何候选改成已批准。

- 付费生成和重试按任务一次授权，后续会话继承剩余额度。优先复用用户已确认对象、次数及既有有界重试合同；必要信息缺失时首次执行前集中列明具体提交方案，不要求已清晰授权的工作重复确认。
- 额度以实际请求计数，区分任务总上限、逐对象上限与具体操作类型。内部重试也计实际调用；结果未知或可能已送达的请求先占额。本地 FAILED、解析失败或超时不是未计费证明；费用未知明确记为未知。
- 已知证明未发送的尝试另行记录，不虚增实际远端提交；相同幂等键恢复查询不记为新的生成提交。没有可靠消费记录时先核对尝试/回执，不推断无限额度。
- 本文的记录用于 Codex 核对，不能作为程序已实现原子额度扣减或强制费用上限的证明。并行操作优先依靠既有运行锁、幂等与任务事实，不能凭两份记录各自认为仍有额度就重复提交。

## 4. 既有恢复与质量门槛

- 项目级前置导演依 `USER_DECISIONS.md` §5.4、§10.6 使用现有人工免证据恢复和审计；同输入复用须通过原完整性检查，输入变化按原规则明确确认。内部重试上限仍依 §5.16。
- 分组导演、故事板、H3 不获得上述豁免，仍按对应证据、状态和手动触发合同执行。H3 取消与重新生成仍为两个独立动作；未知态不得当作失败自动重提。
- `USER_DECISIONS.md` §12、§13 及验收 §15、§16 是历史单次例外。文档记载已完成的操作只作证据，不转为未来或下一轮许可，也不伪造远端未受理。
- 真实配音、实测时间轴、冻结快照、导演校验、不可变资产、所有权和删除确认要求均按原规则执行；一般授权记录不覆盖这些门槛。

## 5. 操作记录的最小内容

具体操作在既有 `runtime/operations/` 下单独记录并由索引引用；可以是 Markdown 或已有 JSON 格式，不新建数据库。保留原始授权与后续变更、执行结果，不覆盖历史事实。

| 必填信息 | 记录方法 |
| --- | --- |
| 操作身份与状态 | 操作 ID、任务目标、业务项目/组/镜头等精确对象；待批准/有效/完成/撤销/额度耗尽/待补充，不将业务远端 UNKNOWN 改成授权失败 |
| 用户授权证据 | 用户原话或明确操作、日期、会话/消息定位、对应已展示的具体方案；准确口令如适用须保留其限定冲突范围 |
| 允许范围 | 动作、输入版本或允许修复边界、模型/参数限制、接收方/用途/数据类型，必要时引用已批准长期许可 |
| 上限与消耗 | 逐目标及总提交上限、实际提交、未决尝试、剩余额度、费用已知值或未知；仅规则修改且未授权生成时明确写生成额度为零 |
| 实际执行证据 | 已有 run/attempt/generation ID、幂等键、请求/结果哈希或原审计位置；无实际提交就如实记录无 |
| 失效与续接 | 完成、撤销、耗尽及实质变更条件，尚可继续的查询/归档范围，以及后续会话更新记录的依据 |

任务记录应能追溯现有事实，不复制业务正文、秘密或无关用户数据；索引仅保存定位所需的信息。

## 6. 自动审批与检查

需审批时提供原授权来源、具体动作/接收方/对象、限制和剩余额度；既有授权有效就引用证据，不先要求用户重新批准。自动审批仍独立判断；拒绝后如实报告具体原因和缺口，按原批准范围处理可继续部分，不换通道绕过。

验收按 `FINAL_ACCEPTANCE_CRITERIA.md` §17，以实际加载的指令、记录查找和只读场景检查为依据，未实际执行的项目验收不得勾选通过。
